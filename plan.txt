Elemental Duel — complete build plan
Research and asset shortlist · Updated October 10, 2026 · Godot 4 · Windows laptop · 1v1 3D PvP
My recommendation is to build this in Godot 4.7.2 using GDScript, with CC0 visual/audio assets and simple custom gameplay code. Godot is free, open-source and released under the MIT license; its official Windows download page lists version 4.7.2, dated August 18, 2026.

Permissive code: MIT
MIT-licensed controllers and libraries can generally be reused in commercial games, but you must retain their copyright and license notices when redistributing the covered code.



What nobody can guarantee
No website can promise that nobody will ever complain or that an uploaded file has no third-party rights issues. Even a CC0 asset is not a blanket guarantee about trademarks or unrelated rights. Keep the original license evidence for every download.



I have prioritised CC0 asset pages and identified MIT code separately. Avoid packs labelled merely free, royalty-free, personal use only or non-commercial unless their terms have been checked.

My choice: use Quaternius RPG characters first. If their included animations are insufficient, test the Universal Animation Library and retarget the clips to your character's skeleton.
Required animation states: idle, walk, run, strafe, cast, hit reaction and death. The spatial jump can initially use a short disappearing/appearing effect instead of a complicated movement animation.
A single connected, properly skinned character mesh is preferable to separately assembled body parts. The skeleton should deform the mesh naturally, preventing visible gaps around the shoulders, elbows, hips and knees.

Important: for version one, make the actual arena yourself using basic Godot meshes. Downloaded environment art should be decoration, not the thing that determines whether players fall through the floor or cross the boundary.
Recommended layout:
- Arena radius: approximately 12 metres.
- Flat floor with a solid collision shape.
- Continuous circular perimeter wall.
- Two spawn positions on opposite sides.
- No pits, moving platforms or destructible environment.
- Temporary earth walls are separate objects, not permanent arena geometry.
For a reliable collision boundary, create a ring of overlapping wall segments or a suitable continuous collision mesh. Do not rely on the visible wall model as the only protection.

Exact implementation plan for the six abilities
Ability	Implementation
Fireball	Small emissive projectile, orange particles, collision and a short burn effect
Water rocket	Fast blue projectile with a small splash and mild knockback
Earth wall	Spawn a temporary stone mesh with its own collision shape
Wind push	Directional cone or sphere-area effect, applying limited pushback
Lightning	Brief warning marker, followed by a lightning strike in a defined area
Spatial jump	Short-lived glowing ring at the origin and destination, then teleport
For effects, prioritise clear hit feedback over visual complexity. Players need to see where lightning will strike and where a spatial jump will land.

A useful Godot scene structure is:
Player (CharacterBody3D)
├── CollisionShape3D
├── CharacterMesh
│   └── Skeleton3D
├── AnimationTree
├── CameraPivot (Node3D)
│   └── SpringArm3D
│       └── Camera3D
├── AimOrigin (Marker3D)
└── SpellSpawn (Marker3D)


This is a scene-structure blueprint, not a complete working project.
Aiming rule: cast a ray from the centre of the camera view to find the intended target point. Spawn the projectile at the player's casting position and direct it toward that point. This prevents projectiles from appearing to miss when the character is off-centre on the screen.
For the spatial jump, derive a safe target from the camera direction, validate the landing point against the arena and other characters, and then teleport. Never blindly add the camera's forward vector to the player's position.

Use Area3D for simple hit detection, CharacterBody3D for players and walls, and ray or shape casts for fast projectiles to avoid skipping through targets between physics frames.
For multiplayer, the server must validate hits, damage, cooldowns, SP and teleport destinations. Client-reported results should not be trusted. Godot's multiplayer documentation specifically recommends authoritative handling of gameplay-critical state.

The full step-by-step build order
Follow this sequence; each phase should work before moving to the next.
01

Create the project and establish licensing
Install Godot, create the project, choose a renderer, initialise Git, and create a LICENSES folder. Save each asset's source URL, license and original license file. Include the Godot MIT notice when distributing the engine.



02

Build the empty arena
Create the circular floor, perimeter wall, lighting and two spawn locations using primitive meshes and static collision bodies.



03

Make one character move perfectly
Add the capsule collider, WASD movement, camera orbit, mouse aiming and collision handling. Test against the arena boundary before importing animations.



04

Add two complete characters
Import one suitable model, get the skeleton and animations working, then duplicate it with a distinct appearance. Add the second player's collision and spawn position. Prevent overlapping characters.



05

Implement HP and the six base abilities
Create a single authoritative health system and implement fire, water, earth, wind, lightning and spatial jump individually. Confirm that all six work before introducing combos.



06

Add double and triple combinations
Store combination definitions in one data table. Resolve three-key combinations before two-key combinations, and two-key combinations before single spells. Treat key order as irrelevant if that is the intended design.



07

Implement safe spatial jumping
Check the landing point, ensure the destination lies within the playable circle, avoid walls and characters, and deduct SP only for successful jumps. Regenerate SP over time.



08

Add visuals, sound and HUD
Introduce the selected particle effects, spell sounds, HP/SP bars, ability indicators and hit feedback. Keep the screen readable even when several effects overlap.



09

Test local combat exhaustively
Verify collision, damage, combo timing, simultaneous hits, wall placement, cooldowns, SP regeneration and the round-end condition. Repeat difficult cases rather than testing only the normal path.



10

Add online PvP last
Implement host/join, server-authoritative movement and spell resolution, synchronised HP/SP and a match-end state. Test on two separate computers before attempting public matchmaking.



9. Final decisions to lock before you build
Design decision	Recommendation
Movement	WASD, camera-relative
Six ability inputs	Q, E, R, F, C, Space
Combos	Buffer rapid inputs; longest valid combo takes priority
SP	Starts at 100; spatial jump costs 35; regeneration delayed briefly after use
Arena	Circular, flat, enclosed, with no environmental hazards
Character bodies	Continuous skinned meshes, capsule physics
Combat authority	Server decides damage and match results online
Game modes	One training mode first, then host/join 1v1
First release	One arena, two characters, six abilities and a small, balanced combo set
One final design warning: elemental combos create more interactions than they appear to. Five ordinary elemental keys already yield 10 possible pairs and 10 possible three-element combinations. Build the combo system so new combinations are data entries rather than new custom code paths. Start with a handful of combinations, test their counters, and expand to the full library only when the base combat feels good.
Your first playable milestone should be two characters in a circular arena, moving smoothly, casting six basic abilities and reducing each other's HP to zero without falling through the floor, clipping through walls or overlapping bodies. Once that works, the rest becomes an incremental game-development task rather than a large, tangled project.
